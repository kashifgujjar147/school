# v1.2 features: parent portal, notifications, fees, ID cards, analytics

This page is for the person who installs and configures a school. It covers what each feature
needs before it works and what happens when that setup is missing.

## Upgrading an existing installation

Start the new version as usual. On start-up, migration 3 runs once. It only **adds indexes**: it
does not drop indexes, rewrite documents or touch existing data. Every new field is optional and
has a default, so records created by v1.0/v1.1 keep working unchanged. Take a backup first anyway
(Admin → Backups).

## Parent portal (Standard package)

1. Admin → Guardians: add the guardian and link them to each of their children from the student's
   profile. One guardian can be linked to several children.
2. In the Guardians list, choose **Create portal account**. Leave the password empty to generate
   one; it is shown once to hand to the parent.
3. Parents sign in at `/parent/login`. They see only the children linked to their guardian record.

Parents can change their password under Account. A forgotten password goes through the existing
reset flow: the request reaches administrators, who issue a reset link or temporary password from
Users. Suspending the account (Guardians list) signs the parent out everywhere.

## Notifications: SMS and WhatsApp (Standard package)

Admin → Notifications:

- **Automation**: switch on the events (absent / late / leave, fee due, fee paid, results
  published, homework, announcement) and the channels (SMS, WhatsApp).
- **SMS provider**: unchanged from v1.0 (Twilio or an HTTP gateway).
- **WhatsApp**: needs a Meta WhatsApp Business Cloud API access token and phone number ID. Messages
  the school starts must use a template that Meta has **approved**, with one body variable
  (`{{1}}`); enter its name and language. For delivery statuses, set the app secret and a verify
  token, and register `<APP_URL>/api/webhooks/whatsapp` in the Meta app's webhook settings.
- **Send announcement**: publishes to the parent portal and queues messages to guardians.

If a channel has no provider configured, its messages wait in the queue with the status
**blocked_config**. They are never shown as sent. Once the provider is configured, the queue
retries them automatically.

## Fees and online payments

Admin → Fees: issue vouchers to one student or a whole class, record cash, bank or cheque payments,
and download vouchers and receipts. Amounts are stored as whole paisa, so no rounding is lost.

Online payment is optional and uses **Stripe Checkout**. Configure it under Fees → Fee settings, or
with `PAYMENT_PROVIDER=stripe`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` and `PAYMENT_CURRENCY`.
Then, in the Stripe dashboard, add a webhook endpoint at
`<APP_URL>/api/webhooks/payments/stripe` for these events: `checkout.session.completed`,
`checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed` and
`checkout.session.expired`. The payment currency must match the fee currency. Check that your Stripe
account supports that currency.

A payment is recorded only after both of these happen:

1. a webhook arrives whose signature verifies;
2. the checkout session is re-read from Stripe's API, and it is paid with exactly the expected
   amount and currency.

A replayed or duplicate callback is ignored. If the amounts differ, the payment is marked
`amount_mismatch` and is not applied, so staff can review it. Card details never reach the school
server.

Until a provider is configured, parents see "Online payment is not available yet" and pay at the
office or bank with the printed voucher.

Online payments must be started on the internet-facing server that Stripe calls back, which is the
cloud server in hybrid setups. The resulting payments are synchronised to local servers as usual.

## Student ID cards

Admin → ID cards, or a student's profile, produces print-ready PDFs in two layouts: an A4 sheet
with 10 cards per page, or a single card for card printers. Each QR code links to
`<APP_URL>/verify/<token>`. The token is random (192 bits) and cannot be guessed from student data.

Anyone who scans the card sees only the school name, the student's name and class, and whether the
student is currently enrolled. **Revoke & reissue** invalidates every previously printed card for
that student.

Student photos print when they are PNG or JPEG. WebP photos fall back to the student's initials.

## Analytics

Admin → Analytics (principal and admin) computes every figure from live records, for a date range
and an optional class filter. It covers attendance trends and attendance by classroom, fees
collected, outstanding and overdue, exam averages and pass rates, admissions, and comparisons with
the previous period and the same period last year.
